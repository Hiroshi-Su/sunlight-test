# 描画の方式：WebGPU と WebGL2

映像（visuals・検証・展示）と room モードは、**WebGPU** で描く。WebGPU が使えない環境では、自動で **WebGL2** に切り替わる。どちらで描いても同じ映像になるように、シェーダー（GPU で動く計算）を 2 つの言語で同じ内容に書いている。

- 対象コード：`src/gpu/`（WebGPU の土台）、`src/stage.ts`（WebGL2 の土台と共通の形）、`src/scenes/`（映像。GLSL と WGSL の両方）、`src/room/`（room モード。`core.ts` が共通の計算、`gl.ts` が WebGL2、`gpu.ts` が WebGPU）
- 開発用の Mac（Apple M4）の Chrome とヘッドレスの Chrome、Electron 44（Chromium 152）で確認した

---

## 1. 2 つの方式

| | WebGPU | WebGL2 |
|---|---|---|
| シェーダーの言語 | WGSL | GLSL |
| GPU への命令の出し方 | 直接（`src/gpu/`） | three.js を通す |
| Mac での中身 | Metal | ANGLE が Metal に変換 |
| Windows での中身 | Direct3D 12 | ANGLE が Direct3D 11 に変換 |
| 使える環境 | Chrome・Edge 113 以降、Electron（この作品の Electron 44 で確認） | ほぼすべて |

どちらも、描く映像の絵は同じ（2 章）。WebGPU の方がわずかに軽い（3 章）。

### 1.1 どちらで描くかの決め方

1. URL に `?gpu=webgl` があれば WebGL2
2. そうでなければ WebGPU を準備する。GPU（アダプター）や装置（デバイス）が得られなければ WebGL2

どちらで描いているかは、visuals・検証の状態表示の 1 行目（`FPS 60.0  描画 WebGPU`）と、room モードの状態表示（`描画 WebGPU`）に出る。

### 1.2 作り方

**映像**：各映像は、GLSL と WGSL の 2 つのシェーダーと、値（uniform）の一覧を持つ。値を計算する JavaScript は 1 つで、2 つの方式で共通。

- 値の一覧は WebGL と同じ「名前 → `{ value }`」の形。WebGPU では、値の種類（数・`Vector2`〜`4`・`Matrix4`・数の配列など）から WGSL の構造体を自動で作り、毎フレーム同じ並びでバッファに書き込む（`src/gpu/layout.ts`。並べ方の規則は `tests/gpu-layout.test.ts` で確認）
- WGSL の中では値を `u.名前` で読む。映像は `fn frag(p: vec2f) -> vec3f` を書けばよい。`p` は WebGL の `gl_FragCoord.xy` と同じ向き（左下が原点）にそろえてある
- 画像（写真）は、WebGL（three.js）と同じく上下を反転して GPU に載せ、ミップマップ（縮小した画像の段）も WebGL と同じ作り方にそろえた（4 章）

**room モード**：1 フレームごとの値の計算（日差し・雲・波・重ね合わせの重み・光の揺らぎを描く網目の一覧）は `src/room/core.ts` にまとめ、2 つの方式が同じ値で描く。WGSL には WebGL の `out` 引数がないので、関数の戻り値を構造体にするなど形は少し変えたが、計算は 1 行ずつ同じにしている。

### 1.3 WebGPU で気をつけていること

| 項目 | 内容 |
|---|---|
| 座標の上下 | WebGL は左下、WebGPU は左上が原点。計算は WebGL と同じ向きで行い、画像を読み書きするところだけ上下を入れ替える |
| 画像を読む場所 | WGSL では、分岐やくり返しの中で「ぼかしの段を自動で決める読み方」ができない。そのため段をいつも指定して読む（写真は 0 段目。写真と画面の画素はほぼ 1 対 1） |
| 予約語 | `target` などは WGSL の予約語で、名前に使えない |
| シェーダーの誤り | WebGPU の命令の誤りは、黙って描かれなくなるだけで気づきにくい。画面の console とアプリのログ（`gpu-error`）に最初の 20 件を出す |
| 装置が失われたとき | ドライバの再起動などで GPU の装置が失われたら、アプリ本体に知らせて読み込み直す（`gpu-device-lost`。WebGL のコンテキストが失われたときと同じ復帰の仕組み） |
| GPU 時間の表示 | `timestamp-query` で映像と最終処理の時間を計る。Apple の GPU では、前後のフレームの処理が重なって大きく出るので「参考値」と表示する（WebGL と同じ）。正確な重さはベンチマークで見る |

## 2. 同じ絵になるかの確認

### 2.1 映像

visuals の各映像を、同じ日時（`?t=2026-12-21T10:00`）・同じ動きの時間（`?animTime=100`、2.3 節）で、WebGL2 と WebGPU の両方で描き、画面を撮って画素ごとの差（0〜255）を比べた。

| 映像 | 差の平均 | 99% の画素の差 | 差が 8 を超える画素 |
|---|---|---|---|
| 検証用：光の向き | 0.56 | 1 | 0% |
| 光の時計 | 0.56 | 1 | 0% |
| にじみ | 0.53 | 1 | 0% |
| 光の柱 | 0.57 | 1 | 0% |
| 光の雲 | 0.56 | 1 | 0% |
| 画像：元の写真 | 0.56 | 1 | 0% |
| 画像：結露・水滴 | 0.65 | 2 | 0.05% |
| 画像：分光 | 0.61 | 1 | 0.08% |
| 画像：水面 | 0.55 | 1 | 0% |
| 画像：光のにじみと等高線 | 1.70 | 33 | 2.26% |
| 画像：陽炎 | 0.56 | 1 | 0% |
| 画像：垂れる流れ | 0.56 | 1 | 0% |
| 画像：ピクセルの引き伸ばし | 0.71 | 2 | 0.54% |

- 差の平均 0.5 前後は、8bit の縞を防ぐために毎フレーム加える乱数（ディザ、±0.5）の違いで、絵としては同じ
- 「光のにじみと等高線」は、強くぼかした写真（ミップマップの 5 段目）の明るさで等高線を引くので、ぼかした画像のわずかな違いで線の位置が少し動く（2.26% の画素）。見た目の印象は同じ
- 「ピクセルの引き伸ばし」「分光」「結露・水滴」の少数の画素は、明るさのしきい値のちょうど境目で結果が分かれたもの

### 2.2 room モード

乱数で光線を選ぶパストレーシングも、画素ごとの乱数の種を WebGL と同じにしてある。止めて数秒重ねたあと（1 画素あたり数百本）の絵を比べた。

| 場面 | 差の平均 | 最大の差 |
|---|---|---|
| 冬至 10:00、右の窓 | 0.00 | 1 |
| 夏至 12:00、天窓 | 0.00 | 1 |

水盤・海・水面の反射・雲・スクリーンの映像をすべてオンにした場面は、波と雲が実際の時間で動いて同じ瞬間を撮れないので、見比べて同じ見え方であることを確かめた。窓の位置の切り替え（部屋を作り直す）を繰り返しても、エラーは出ない。

### 2.3 見比べのための URL

| URL | 内容 |
|---|---|
| `?gpu=webgl` | WebGL2 で描く（既定は WebGPU。使えなければ自動で WebGL2） |
| `?animTime=100` | 映像の動きの時間を 100 秒で止める。2 つの方式の見比べや、同じ絵の撮影に使う（room モードの波と雲には効かない） |

## 3. 重さ（Apple M4）

### 3.1 映像（3840×1080、visuals のベンチマーク）

| 映像 | WebGL2 | WebGPU |
|---|---|---|
| にじみ | 10.21 ms | 10.26 ms |
| 光の雲 | 3.99 ms | 3.68 ms |
| 分光 | 3.85 ms | 3.96 ms |
| 結露・水滴 | 3.63 ms | 3.41 ms |
| 光の柱 | 3.06 ms | 2.59 ms |
| 陽炎 | 2.58 ms | 2.34 ms |
| 光のにじみと等高線 | 2.09 ms | 1.95 ms |
| 水面 | 1.78 ms | 1.52 ms |
| ピクセルの引き伸ばし | 1.66 ms | 1.48 ms |
| 検証用：光の向き | 1.65 ms | 2.04 ms |
| 垂れる流れ | 1.40 ms | 1.14 ms |
| 元の写真（効果なし） | 1.23 ms | 0.93 ms |

- 多くの映像で、WebGPU の方が 0.1〜0.5 ms 軽い。効果なしの写真で 0.3 ms 軽いので、1 フレームごとの決まった手間が少ないと考えられる
- 計算の重い映像（にじみ・分光）はほぼ同じ。GPU の計算そのものは、どちらの方式でも同じ Metal の命令になるため
- 計測したときは、電池の残りが 20% を切って Chrome の省エネ機能が働いていた（画面の更新が 30fps に抑えられる）。2 つの方式は同じ条件で測ったので比べられるが、値そのものは docs/visuals.md 10.2 節の表とは直接比べないこと

### 3.2 room モード（描画範囲 1084×760、パネルの「重さを測る」）

| 設定 | WebGL2 | WebGPU |
|---|---|---|
| 既定（照り返し 3 回） | 6.8 ms | 6.4 ms |
| 雲・スクリーンの映像・水盤・海・水面の反射をすべてオン | 16.7 ms | 12.7 ms |

すべてオンにすると、WebGPU の方が約 24% 軽い（光の揺らぎを描く網目が多いほど、命令を出す手間の差が効く）。

## 4. ミップマップをそろえた理由

「光のにじみと等高線」を最初に比べたとき、等高線の島の大きさが方式によって違い、15% の画素に差があった。原因は 2 つあった。

1. **画像の載せ方の上下**：three.js（WebGL）は写真を上下反転して GPU に載せる。WebGPU で反転せずに載せると、ミップマップの段の大きさが奇数になるところ（3024 → 1512 → 756 → 378 → 189 → 94）で、2×2 の画素の組み方が上と下で逆になり、ぼかした画像がずれる。WebGPU でも反転して載せるようにした（差 15% → 7%）
2. **縮め方**：Metal の自動のミップマップは、次の段の画素の中心に当たる位置を線形補間で読む作り方で、奇数の大きさでは位置が少しずつずれていく。単純な 2×2 の平均ではなく、同じ作り方にした（差 7% → 2.3%）

## 5. 分かっている課題

1. **Windows では未確認**：Windows の WebGPU（Direct3D 12）では、まだ動かしていない。展示用 PC を Windows にする場合は、全映像を `?gpu=webgl` と見比べる（2.1 節と同じ方法）
2. **2 つの言語を保つ手間**：映像を直すときは、GLSL と WGSL の両方を同じように直す必要がある。値の名前の食い違いは `tests/wgsl.test.ts` が見つけるが、計算の中身の食い違いは見つけられないので、2.1 節の方法で見比べる
3. **WebGPU ならではの機能はまだ使っていない**：汎用の計算（コンピュートシェーダー）を使えば、ピクセルソートの本来の並べ替え方式や、液体の流れのシミュレーションなどが作りやすくなる
